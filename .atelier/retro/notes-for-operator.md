## Preflight is all-green on a condition that stops the run in 0.4s

**2026-09-04, `/prototype-auto learn-anywhere`, framework `0.1.0-dev`.**

`atelier prototype run <slug> --auto --preflight` reported **all 17 checks
green**. The run launched, and died 0.4 seconds later having advanced nothing:

```
m1 stop: prototype worktree .worktrees/prototype-learn-anywhere has
uncommitted changes — cannot start a round: M .atelier/atelier.yml,
M .claude/commands/promote.md, ... (+2 more)
```

**A clean prototype worktree is a precondition of starting a round, and
preflight does not check it.** That is the gap, and it is a cheap one to close:
the predicate already exists in the tournament's own guard, and it is a
`git status --porcelain` on a path preflight already knows.

Three things make it worth filing rather than shrugging at.

- **The all-green is actively misleading.** Preflight checks seventeen things,
  several of them far more exotic than this — that the worker binary resolves,
  that numeric env overrides parse, that gate commands execute in a *fresh*
  worktree, that the current milestone is decidable on this host. A checklist
  that thorough reading green is a promise the run will at least *start*.
- **The dirt was the framework's own.** All 39 changed lines were Atelier
  scaffold regenerated by `atelier refresh` / `init` — a `bootstrap:` block in
  `.atelier/atelier.yml`, the memory-routing block in `CLAUDE.md`, and one
  `description:` frontmatter line in each of four `.claude/commands/*.md`.
  Nothing a human edited. So the framework dirtied the worktree and then
  refused to run because the worktree was dirty.
- **The failure reads as a plan problem.** The envelope surfaces
  `"reason": "lane not green (state='stopped') — must-stop"`, and the run
  record's `terminal_causes` and `session_diagnostics` are both `[]`. The
  actual cause appears **only** in
  `.specs/.orchestra/events/prototype-<slug>.jsonl` at
  `prototype.milestone.outcome`. The boundary classifier's own comment
  acknowledges this ordering ("returns BEFORE the gate/benchmark live-re-hash …
  the ordering only affects the human reason") — but here the consequence is
  that the single most-read field names a symptom two layers downstream of the
  cause. Worth carrying the milestone-outcome reason into `stop_reason` when
  the run stopped before any round began.

**Recovery, which worked and is worth knowing:** stash the scaffold in the
prototype worktree (`git stash push -u`, reversible — discarding also works but
is not), then `atelier prototype goal approve-boundary <slug> <id> --redo` to
release the lane from `stopped`/`running` back to `approved`. `--redo`
preserves the frozen gate hashes, so no re-approval is needed. With
`rounds: []` nothing real is archived.

**Related, same session:** `approve-milestone <slug> 1 2 3 4 5` is the
multi-id re-freeze form, and it exists precisely for the case where a
deliberate harness commit lands after the freeze. It appends new approval rows
rather than overwriting, so the audit trail survives. That part worked well.

## `chain_rounds` falls through to mainline on a barren round, discarding the tree

**2026-09-05, `learn-anywhere` m1, framework `0.1.0-dev`. VERIFIED by git sha.**

`run.chain_rounds: true` is documented as "start round N+1's FIRST variant seat
from round N's best retained branch instead of from mainline." It chains from
**round N only**. When round N is barren — the worker ran, found nothing to fix,
and committed nothing — round N's branch has no retained work of its own, and
round N+1 forks from **mainline**, discarding everything rounds 1..N-1 built.

Observed, by sha:

| round | branch tip | carries the work |
| --- | --- | --- |
| r1 | 2 commits | yes |
| r2 | `6a8813e` (3 commits) | yes |
| r3 | `6a8813e` — *identical to r2, committed nothing* | inherited only |
| r4 | `97a1a2e` = mainline | **no — chain broken** |

So the final round of a 4-round budget rebuilt from scratch work that already
existed and passed. `git log 97a1a2e..HEAD` in r4's worktree was empty.

**The fix is a fallback, not a redesign:** chain from the most recent round whose
tree **passed the gate**, not from `N-1` unconditionally.

> **Corrected 2026-09-18.** This originally said "the most recent round that
> actually produced commits", and that the barren round was "evidence the tree is
> already good." Both were wrong, and the section "A worker dispatched onto a
> green tree broke it…" below is the proof: r6 produced
> a commit — on a red gate — and chaining from it is exactly how r7 inherited a
> broken tree. "Moved" is not "good". The only chain base worth having is one the
> gate has read green.

## A green worker view and a stuck driver verdict, with no feedback between them

**Same run, r3. Observation, not a confirmed root cause.**

> **Resolved 2026-09-18.** Both halves were right. The gate *was* green, so the
> seed correctly named no failing check; the driver declared `stuck` because its
> SLO reading was the stack-down sentinel — the benchmark runs without `serve:`
> (last section of this file). Nothing about r3's seeds was a regression of A1.

Round 3 took **8 gate readings, all 8 green** (`auth_contract_violations=0`,
`auth_flows_swept=4`, zero serve failures) and was still terminated `stuck`
with `gate_passed: false` and `benchmark_value: null`.

Its inter-cycle worker seeds were **byte-identical**, with no failing-scenario
tail — the shape §4-C of `PROTOTYPE-LANE-ISSUES.md` recorded as the A1 baseline
("the seed is re-sent verbatim every cycle"). One of the four was an autocompact
continuation summary, so 150k was being hit inside a 30-minute round.

**Stated carefully:** identical seeds are *correct* when the gate is green,
because there is no failure to report. What does not reconcile is a driver that
saw enough failure to declare `stuck` while sending a seed that named none. One
of those two is wrong, and the artifacts do not say which — the per-round
`terminal_cause` is only persisted at milestone finalization, so a run killed or
stopped mid-milestone loses exactly the field that would settle it. **Persisting
`terminal_cause` per round as it happens would make this diagnosable.**

## The one non-green reading in the whole run was infrastructure

> **Corrected 2026-09-18 — the causal claim below is wrong.** Round 2's
> `bench=1.0` was not an unlucky sample of a flaky stack: the benchmark runner
> never boots `serve:` at all, so the benchmark reads the stack-down sentinel
> **every time**. Reproduced; see "The benchmark runs without the stack" at the
> end of this file. The reading quoted below was a real gate-side emulator death,
> but it is not what cost round 2 its verdict, and the "~96% reliable, decided on
> one draw" framing should be discarded. The coverage-floor point stands.

Across r2 and r3 on tree `6a8813e`: **27 gate readings, 27 green.** The single
non-green reading anywhere in the run was:

```
"serve_failed": true, "died_mid_run": true
ATELIER_METRIC auth_flows_swept=0
ATELIER_METRIC auth_contract_violations=1
```

Zero flows swept — the emulator stack died, and the `1` is the stack-down
sentinel added by `97a1a2e`, not an auth defect. That one unlucky reading was
what the benchmark happened to sample, and it cost round 2 its verdict.

Two things worth keeping from this:

- **The coverage floor worked.** `coverage_min: 4` on `auth_flows_swept` means a
  stack-down reading (0 swept) can never be read as green. The lane can fail
  falsely *stuck*, but not falsely *green* — which is the direction you want,
  and is §"A green gate is not evidence of work" doing its job.
- **The benchmark's single sample is the weak link.** A gate that is ~96%
  reliable under machine load decides a milestone on one draw. Sampling the
  benchmark more than once, or re-drawing when `serve_failed` is true, would
  remove the coin flip. Note machine load at the time: **load average 15.9**,
  409k pageouts, with an unrelated Playwright suite, a Cloudflare `workerd` and
  Microsoft Defender all competing.

## A worker dispatched onto a green tree broke it, committed on red, and the chain carried it forward

**2026-09-05 run, diagnosed 2026-09-18 in an adversarial review with codex.
VERIFIED from the r6 transcript and by sha.** Full write-up:
`research/prototype/learn-anywhere-plan-review.md`.

The base was `6a8813e`, on which the m1 gate had read green 27 times. The
pre-green shortcut's gate probes were green; its SLO probe read
`auth_contract_violations = 1.0` — the stack-down sentinel, because the
benchmark runs without `serve:` (next section). So the driver dispatched a worker
with, verbatim: *"the gate is green but this is NOT a green boundary … THE GATE
IS ALREADY GREEN … Your objective this cycle is the SLO NUMBER."* The number
could not move. In order:

```
gate(4,0) -> gate(4,0) -> EDIT auth-src.mjs x2 -> EDIT build.py
          -> gate(4,3) -> gate(4,3) -> gate(4,3) -> gate(4,3) -> COMMIT e5c8bef
```

Four flows swept and three failing — full coverage, so the contract, not the
stack. It committed anyway. `chain_rounds: true` then made `e5c8bef` round 7's
base, so r7 started from the broken tree. The same commit also added a
`preconnect`/`dns-prefetch` to `apis.google.com` on every page, which the m4
harness cannot see: resource hints raise no Playwright `request` event.

Three framework points, most important first:

- **A worker was ordered to move a number no code change could move.** The
  prompt already tells a worker when the gate is green — that part works. What
  failed is the reading it was told to act on. A metric reading taken with
  coverage 0 (`auth_flows_swept=0`) is not a reading of the metric, and the
  coverage floor already knows this at the *boundary*; the pre-probe and the
  checkpoint should apply the same rule and refuse to dispatch on it. Given a
  real-looking target and no way to hit it, the worker did what workers do:
  rewrote the code it was pointed at.
- **Committing on a red gate should not survive into a chain base.** The driver
  auto-commits at cycle end as a backstop, which is right for persistence and
  wrong for chaining. See the corrected fallback above.
- **The certification path that works** is `goal accept-result <slug> <id> --value N`
  (operator-only), after two logged `prototype check --milestone <id>` runs on the
  base. It records the round as `operator_accepted`, `method:
  operator_accept_result`, `graft: "no git graft"` — the provenance named, not
  laundered through `--accept-empty-graft`. `--milestone` matters: without it the
  check runs the slug-level file, not the frozen sidecar.

## The benchmark runs without the stack, so no served milestone can ever go green

**2026-09-18. VERIFIED by reproduction. The most consequential finding in this
file** — it makes every milestone of a served lane uncertifiable by the
tournament, and it is the root cause of the r6 regression above.

The gate and the benchmark run the same harness script through two different
paths:

| | path | boots `serve:`? | m1 reading on `6a8813e` |
| --- | --- | --- | --- |
| gate | `atelier prototype check` | **yes** | `auth_flows_swept=4`, `auth_contract_violations=0` |
| benchmark / SLO probe | `_goal_tournament.default_bench_runner` → `subprocess.run(["bash","-c", cmd], cwd=worktree)` | **no** | `auth_flows_swept=0`, `auth_contract_violations=1` |

Neither `_call_bench` call site (`_goal_tournament.py` ~2171, ~2466) wraps the
call in a serve lifecycle. With no `ports.json` the harness emits its
stack-down sentinel. Run with no stack up, every benchmark in this lane reads:

```
m1 auth_contract_violations=1   auth_flows_swept=0      (need 0, >=4)
m2 sync_mismatches=1            sync_roundtrips_swept=0 (need 0, >=4)
m3 rhythm_defects=1             rhythm_days_swept=0     (need 0, >=4)
m4 silent_network_ops=0         sync_states_surfaced=0  (need 0, >=4)
m5 p95_interaction_ms=99999     speed_probes_swept=0    (need <=100, >=3)
```

Consequences, in order of cost:

- **No milestone can reach a green boundary through the tournament.** Every
  m1 SLO reading ever taken in this lane — Sep 5 r2's `bench=1.0`, and the
  Sep 18 pre-probe's `1.0` — was this sentinel. Four days of diagnosis went to
  machine load, rate limits and DNS, each real, none the cause of a *green* tree
  failing to certify.
- **It turns a green tree into a worker assignment.** The pre-probe dispatches a
  worker to move the number, and the worker rewrites working code (r6).
- **The coverage floor held.** m4 reads `silent_network_ops=0` — a pass on the
  number — and is refused only because coverage is 0. That is the one guard
  that kept this from producing a false green instead of a false red.

**Fix, upstream (preferred):** the bench runner should run inside the same
`serve:` lifecycle the gate uses when the checks file declares one — the
machinery exists in `prototype-cli`. Cheap companion guard: a metric reading
whose coverage metric is 0 is *unmeasured*, and should neither enter the SLO
decision nor seed a worker's objective.

**Fix, project-side:** a `harness/bench.mjs` that boots `serve.mjs`, waits for
`ports.json`, runs the scenario and tears down, with every milestone's
benchmark command pointed at it. That edits frozen gate machinery, so it needs
`approve-milestone` on all five.

**Why nobody saw it:** before `97a1a2e` the harness printed *nothing* with the
stack down, so the benchmark read `null` and the milestone died as
"benchmark produced no value" — which looks like an app that never got far
enough to be measured. The commit that made the harness honest is the one that
made this visible.
